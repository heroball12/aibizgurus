# Experience Center security and privacy

The model's tools accept only Pydantic-validated schema fields and read a synthetic revision or the caller's isolated session state. There are no tools for shell/network requests, environment variables, real CRM, customer accounts, billing, employee data, outbound messages or arbitrary database lookups. User text/tool data cannot expand that allowlist. Prompt instructions alone are not the security boundary.

Public pages require a published/public-access experience. APIs check that setting on every session request. All sensitive session endpoints match an unpredictable UUID **and** an HMAC of the server-side Django browser session key; a copied UUID is insufficient. They enforce expiry/end state and no-store responses. Mutations use POST and Django CSRF protection. Employee demo controls require an active employee/admin/owner account without a revoked demo-access record; management requires owner/admin/superuser.

The fictional dealership CRM's simulated sign-in is deliberately labeled and uses no invented shared password or production credentials. It unlocks only the current browser-bound demo record. Other prospects' sessions and real AIBG CRM records remain inaccessible. Public share links are signed, expire after 60 days, and preserve rep/scenario attribution only. Invalid/revoked links fall back to an unattributed default demo. Assessment provenance is separately signed and limited to seven days.

Model calls use the existing server-side platform key. Error logs include event type, exception class, session identifier and latency—not prompts, customer content, credentials or provider response bodies. Public JSON never exposes provider configuration, protocol/system messages or browser-binding hashes. Customer text is rendered using textContent/Django escaping, not injected HTML.

Limits are shared database counters: public sessions 12/hour/IP; staff 40. Public turns 60/hour/IP and 30/session; staff 180/hour/IP and 100/session. Additional platform model limits and global completion/voice budgets apply. Voice requests are bounded per session/IP/day. Audio bodies are limited to 2 MB; voice is captured for at most 45 seconds. Parallel requests use a lease, last-request idempotency, bounded tool loops and transactional writes; reset invalidates late responses.

No real personal information is required; the default is Demo Customer. The microphone is not recorded to app storage, and no media is cached for offline use. Text conversations persist until reset or retention cleanup. Run `purge_demo_sessions` daily to clear content/fictional CRM records after expiry plus 14 days. Field feedback asks for fictional details only; managers should review freeform notes appropriately.

Axel now asks for basic contact details during intake and recommends fictional phone/email examples. Supplied contacts remain inside the same temporary demo record and are never added to outreach or real leads. Phone/email checks validate format, not identity or deliverability. The financing form accepts only predefined fictional financial profiles and enumerated down payments/terms; there are no SSN, birth-date, bank, document upload or free-entry income fields. Unknown submitted fields are rejected. The model can open the form but cannot submit it. Customer submission is CSRF-protected, rate-limited, browser-bound, idempotent and transactionally coordinated with the conversation lease. No underwriting, eligibility assessment, credit decision, lender request or outbound communication occurs. Reset/retention clears financing and contact state alongside the conversation.

A real Growth Assessment request is a separate voluntary submission through the existing real form. It creates the existing real lead plus attribution, without copying the synthetic customer transcript. Clicking the CTA, booking a fictional test drive, or entering the fictional CRM does not create a real lead.

Physical-iPad voice quality, live provider grounding and Internet latency remain a required field acceptance check. No code-level test can guarantee a generative model never makes an unsupported statement; the interface labels synthetic data and tools anchor operations to verified demo records.
