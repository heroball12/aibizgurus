# Validation and verification

Three distinct subjects, a plain-text body and selected service IDs are required. Server checks structure, limits, control characters/HTML/Markdown, pricing/currency language, guarantees/pressure phrases, configured forbidden phrases, conspicuous integration promises, some fabricated research/staff-replacement language, cold-email conversation assumptions, approved links, selected length and the assessment CTA.

The provider receives a strict JSON schema requiring three subjects, a body and only the selected service IDs. General introductions require an empty service-reference array; a placeholder ID is never sent as the example. Deterministic validation still checks the returned content. Malformed or prohibited model output is discarded and retried once with a reason code. A second rejection returns a safe review error. Provider failures preserve the UI choices and do not create a fake successful draft. Only reason codes and usage metadata are logged for rejected responses; no hidden reasoning is collected. Generation is capped at 30/user/hour, plus existing daily provider budgets. Each provider call has an 18-second timeout and no transport retries; the one policy repair can extend total wait.

Approved HTTPS links may include `www` (as the production Demo Center URL does). Bare `www` links and any full URL outside the exact approved allowlist remain blocked. This applies to generation, saving and copying.

Checkers are deliberately conservative and may flag harmless negated language. They are not a semantic guarantee: the employee still reviews truth, names, tone and suitability.
